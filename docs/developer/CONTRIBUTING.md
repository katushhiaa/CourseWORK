# Як долучитися до розробки (CONTRIBUTING)

## Локальне середовище

1. Клонуй репозиторій `katushhiaa/CourseWORK` та перейди в директорію проєкту.
2. Створи та активуй віртуальне середовище Python (`.venv`).
3. Встанови залежності та інструменти документації (`mkdocs-material`, `mkdocs-mermaid2-plugin`, `mkdocs-git-revision-date-localized-plugin`).
4. Налаштуй змінні оточення (зокрема підключення до `MongoDB`) і запусти локальний сервер або застосунок.

## Стандарти коду та правило супроводу

* Дотримуйся чистої структури модулів у `app/` та перевірок якості коду (`SonarQube` / лінтери).
* Діє правило **«зміна коду = зміна документації»**: разом зі зміною коду або архітектури оновлюй відповідні файли в `docs/`:
  * [System Design Document (SDD)](../architecture/sdd.md)
  * [Infrastructure Specification (ISD)](../architecture/isd.md)
  * [Регламент підтримки](../developer/maintenance.md)

## Definition of Done (`docs-or-don’t-merge`)

Pull request, який змінює публічну поведінку системи (нові або змінені ендпоінти API, змінні середовища/конфігурація, формати запитів чи відповідей), **не зливається (`merge`)** без оновлення відповідних артефактів:

- [ ] **Документація в `docs/`:** оновлено релевантні сторінки бази знань (архітектура, експлуатація, інструкції) та поле `review_date` у front matter.
- [ ] **Контракт OpenAPI (`docs/api/openapi.yaml`):** актуалізовано схеми, параметри, приклади та коди відповідей; перевірено лінтером **Spectral** (`0 errors`).
- [ ] **Журнал змін (`CHANGELOG.md`):** зафіксовано зміну публічної поведінки з прив'язкою до версії або етапу розробки.
- [ ] **Перевірки CI (`markdownlint` та `mkdocs build --strict`):** конвеєр проходить без попереджень і помилок (`Exit Code 0`).
- [ ] **Життєвий цикл застарілих сторінок:** застарілі документи не видаляються безслідно, а переводяться у статус `status: deprecated` у front matter із приміткою та посиланням на актуальний документ.
- [ ] **Теги версій документації:** для мажорних змін документації виставляється Git-тег (`docs-v1.0`, `docs-v2.0`).
