**Ідентифікатор:** `RB-**001**`

**Рівень автоматизації:** `1` (скриптований) — ключові кроки перевірки стану сервісу, запуску контейнерів та відновлення бази даних виконуються готовими консольно-скриптовими командами, але фінальне рішення про застосування резервної копії та контроль цілісності даних приймає черговий інженер, щоб уникнути перезапису актуальних записів під час хибного спрацювання алерта.

## Тригер

Спрацювання критичного алерта **`CourseWORKDatabaseDisconnected`** або **`CourseWORKServiceDown`** у системі моніторингу Prometheus/Grafana, а також фіксація **HTTP**-статусів `**500**`/`**503**` або значення `*database*: *disconnected*` у відповіді `**GET** /api/v1/health`.

## Передумови

- Наявність доступу до вузла розгортання або робочого середовища з встановленими `docker`, `docker compose`, `mongosh`, `mongorestore`, `gpg` та `curl`.
- Наявність прав на керування сервісами/контейнерами та доступ до сховища резервних копій (наприклад, `/backups/mongodb`) разом із ключем розшифрування.

## Покрокові дії

1. **Зафіксувати поточний стан сервісу, контейнерів і логів:**

```bash
   curl -i http://127.0.0.1:8000/api/v1/health
   docker compose ps
   docker compose logs --tail=100 app mongodb

```

1. **Підняти або перезапустити спочатку MongoDB, перевірити готовність БД, а потім запустити сервіс застосунку:**

```bash
docker compose up -d mongodb
docker compose exec mongodb mongosh --eval "db.runCommand({ ping: 1 })"
docker compose up -d app

```

1. **Якщо база пошкоджена або дані втрачено — розшифрувати та відновити останню перевірену резервну копію:**

```bash
gpg --decrypt --output /tmp/backup_latest.archive /backups/mongodb/coursework_20261122.archive.gpg
docker compose cp /tmp/backup_latest.archive mongodb:/tmp/backup.archive
docker compose exec mongodb mongorestore --archive=/tmp/backup.archive --drop
rm -f /tmp/backup_latest.archive

```

## Верифікація

1. Перевірити health-ендпоінт і переконатися у коді відповіді `**200** OK`, `*status*: *ok*` та `*database*: *connected*`:

```bash
curl -sf [http://**127**.0.0.1:**8000**/api/v1/health](http://**127**.0.0.1:**8000**/api/v1/health) | python -m json.tool

```

1. Виконати перевірочний запит читання до **API** (`/api/v1/items`):

```bash
curl -sf [http://**127**.0.0.1:**8000**/api/v1/items](http://**127**.0.0.1:**8000**/api/v1/items) > /dev/null && echo ***API** OK*

```

1. Перевірити останні логи сервісу `app` та `mongodb` на відсутність нових помилок підключення.

## Процедура відкату та ескалація

- **Відкат:** якщо після оновлення конфігурації або міграції сервіс не повертається до робочого стану протягом 5 хвилин, повернути попередній тег/коміт (`git checkout <previous_tag>` або попередній образ), перезапустити `mongodb` та `app` і повторно виконати верифікацію через `/api/v1/health`.
- **Ескалація:**
- **0–15 хв:** черговий інженер / On-Call **SRE** (`@katushhiaa`) виконує кроки 1–3 за цим runbook.
- **> 15 хв (якщо MongoDB не стартує або виявлено пошкодження даних):** ескалація на відповідального за БД / архітектуру даних.
- **> 30 хв (якщо сервіс недоступний або виникає ризик порушення цільового **RTO**):** ескалація на ліда сервісу / керівника проєкту з відкриттям інциденту рівня `**SEV**-1` / `**SEV**-2`.
