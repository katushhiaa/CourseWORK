    Infrastructure Specification Document (ISD)¶

    1. Топологія розгортання¶

    Система підтримує два основні середовища виконання:

    • Локальне середовище (Local Development): Запуск через Python Virtual Environment (.venv) або локальний Docker Compose.
    • Контейнерне / Хмарне середовище (Production/Test): Ізольовані Docker-контейнери для застосунку та MongoDB, оркестровані через CI/CD конвеєри.

    2. Конфігурація середовищ та змінні (Environment Variables)¶

    Для конфігурації використовуються такі змінні оточення (без секретів у репозиторії):

    • PORT — порт запуску вебсервера (за замовчуванням 8000).
    • MONGODB_URI — рядок підключення до MongoDB (наприклад, mongodb://localhost:27017).
    • ENVIRONMENT — режим роботи (development, testing, production).

    3. CI/CD-конвеєр (GitHub Actions)¶

    Згідно з налаштуваннями у .github/workflows/:

    • Стадії: Лінтинг (перевірка стилю коду), запуск модульних тестів (pytest), перевірка якості через SonarQube Quality Gates.
    • Тригери: Події push та pull_request у гілку main.

    4. Моніторинг, резервне копіювання та метрики надійності (RTO / RPO)¶

    • Моніторинг: Логування подій у консоль та інтеграція з SonarQube Cloud для відстеження технічного боргу.
    • RTO (Recovery Time Objective): Допустимий час відновлення сервісу після збою — до 2 годин.
    • RPO (Recovery Point Objective): Допустима втрата даних — до 24 годин (за рахунок щоденного резервного копіювання колекцій MongoDB).

    Див. також SDD та Регламент підтримки.

    Експлуатація, відновлення та резервне копіювання¶

    Розгортання версії та оновлення з міграціями¶

    1. Розгортання: отримати цільову версію/тег коду, зібрати/оновити сервіси (docker compose pull && docker compose up -d --build) та перевірити стан через GET /api/v1/health (очікується 200 OK, "status": "ok", "database": "connected").
    2. Оновлення з міграціями: узгодити зміни схеми даних та публічного контракту з CHANGELOG.md і docs/api/openapi.yaml (згідно з чек-листом docs-or-don’t-merge), застосувати зворотно сумісну міграцію/індексацію в MongoDB до перемикання трафіку на нову версію сервісу.

    Відновлення після відмови та цільові RTO / RPO¶

    • Порядок запуску при відновленні: спочатку запускається та проходить перевірку готовності сховище даних (MongoDB), і лише після підтвердження доступності БД піднімається сервіс застосунку (Python API), щоб уникнути стану degraded і помилок підключення при старті.
    • RTO = 30 хвилин — допустимий час простою з моменту виявлення збою до повернення сервісу у робочий стан (діагностика до 10 хв, підняття/відновлення MongoDB та сервісу до 15 хв, верифікація до 5 хв).
    • RPO = 15 хвилин — допустима втрата даних за часом, задана інтервалом інкрементних копій/журналів змін.

    Політика резервного копіювання (правило 3-2-1)¶

    • Обсяг даних: бази, колекції та індекси MongoDB сервісу CourseWORK, а також конфігурація середовища.
    • Розклад і типи копій: повні копії (mongodump / знімок) — щодня о 02:00; інкрементні копії / логи змін — кожні 15 хвилин (відповідає RPO = 15 хв).
    • Retention: щоденні повні копії — 14 днів, інкрементні — 7 днів, щотижневі контрольні копії — 4 тижні.
    • Шифрування: копії шифруються симетрично/GPG перед збереженням поза основним вузлом; ключі зберігаються окремо від архівів.
    • Правило 3-2-1: 3 копії даних (робоча БД + локальна резервна копія + віддалена копія), 2 різні типи носіїв (диск сервера/сховища + віддалене/об'єктне сховище), 1 копія поза основним майданчиком.

    Процедура тестового відновлення (Restore Drill)¶

    1. Підняти ізольований тестовий екземпляр MongoDB (без впливу на основне середовище).
    2. Розшифрувати та відновити останню повну копію й актуальні інкрементні дані через mongorestore.
    3. Зафіксувати тривалість відновлення та звірити з RTO = 30 хв.
    4. Перевірити цілісність даних і підключення тестового екземпляра сервісу, очистити тестове середовище та записати результат у журнал експлуатації.
